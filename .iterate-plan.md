Last 5 commits introduced a broad feature set:

This is a high-change window touching execution, scheduling, launch integration, and packaging at once.

### Issues found

#### Critical

1. **Suspended jobs can still run in wake recovery**
   - Evidence: suspended checks exist in due/scheduled paths (`src/runner.js:74-76`, `src/runner.js:177-179`) but not in wake path loop (`src/runner.js:248-261`)
   - Root cause: suspension logic was integrated into `runIfDue` and `runJobNow`, but not propagated to `checkMissed`
   - Recommendation: add explicit `isSuspended(jobId)` gate in `checkMissed` before lock acquisition; add regression test in `src/runner.test.js`

2. **Parser and launchd conversion contracts are inconsistent**
   - Evidence: parser emits unsupported tokens (`src/cron-parser.js:81`, `src/cron-parser.js:86-87`) while launchd converter requires strict 5-part numeric-style cron (`src/launchd.js:130-132`, `src/launchd.js:93-116`) and consumes normalized schedule (`src/launchd.js:211-213`)
   - Root cause: human parser expanded faster than launchd conversion semantics and validation
   - Recommendation: either support `@reboot`/`L` explicitly in launchd path or reject with actionable validation before plist generation

3. **Packaging/install portability risk from local dependency and runtime mismatch**
   - Evidence: local file dependency committed (`package.json:47`), project engine says Node >=18 (`package.json:38-39`), resolved Commander requires >=20 (`package-lock.json:127-134`)
   - Root cause: development-oriented dependency wiring and lockfile updates were shipped without portability checks
   - Recommendation: replace `file:../action-burgundy` with publishable dependency strategy and align `engines.node` with actual runtime floor

#### Warning

1. **`clear --namespace` uninstalls jobs but does not unregister file entries**
   - Evidence: namespace branch uninstalls and returns (`bin/cli.js:614-622`), while other clear paths unregister (`bin/cli.js:647-649`, `bin/cli.js:711`)
   - Root cause: command path exits before registry cleanup
   - Recommendation: unregister all registry files in the target namespace (or add explicit namespace-unregister command semantics)

2. **Namespace changes can leave stale/orphaned plists active**
   - Evidence: namespace mutation is allowed (`src/registry.js:143-151`), orphan removal only scans current namespace (`src/launchd.js:487-492`)
   - Root cause: lifecycle logic assumes namespace immutability while registry API allows mutation
   - Recommendation: on namespace update, uninstall old namespace plists before syncing new namespace

3. **Command job stdout/stderr is not captured as intended**
   - Evidence: command execution uses `execSync` with piped stdio (`src/runner.js:31-34`, `src/runner.js:47-52`), while capture mechanism only intercepts process writes (`src/logger.js:232-270`)
   - Root cause: subprocess output is captured in child-process return buffers, not process-level write hooks
   - Recommendation: switch to `spawn`/`execFile` with stream piping to logger, or append `execSync` return output explicitly

4. **`runAllDue` path lacks lock acquisition**
   - Evidence: `runIfDue` executes without lock (`src/runner.js:63-114`) while `runJobNow` acquires lock (`src/runner.js:183-187`)
   - Root cause: lock semantics were added to one execution path but not normalized across all paths
   - Recommendation: enforce locking in `runIfDue` (or centralize execution in a single lock-aware runner)

5. **Load-failure notification uses shell interpolation without escaping**
   - Evidence: direct `execSync` command with interpolated filename (`src/registry.js:213-214`)
   - Root cause: convenience shell string composition instead of argument-safe process invocation
   - Recommendation: move notification through safe helper (or action utility) and escape message text

6. **Launchd tests are integration-heavy and environment-sensitive**
   - Evidence: tests install/uninstall real plists and call suspend/resume directly (`src/launchd.test.js:309-385`), production functions hard-require macOS (`src/launchd.js:279-280`)
   - Root cause: no separation between fast unit tests and macOS integration tests
   - Recommendation: gate integration tests by platform/env flag and keep unit tests hermetic

#### Suggestion

1. **Public library API unexpectedly exits process**
   - Evidence: `runScheduledJob` calls `process.exit(1)` (`src/index.js:36-46`)
   - Root cause: CLI failure semantics leaked into exported library function
   - Recommendation: throw typed errors from library exports and let CLI translate to process exit

2. **JSDoc return signatures are stale after feature additions**
   - Evidence: `runIfDue` JSDoc excludes `'suspended'` (`src/runner.js:61`), `runAllDue` return type omits `suspended` array (`src/runner.js:119`)
   - Root cause: behavior changed without synchronized contract updates
   - Recommendation: update JSDoc and generated types together in the same commit as behavior changes

3. **CLI has dead imports and duplicated command flow**
   - Evidence: unused imports (`bin/cli.js:11`, `bin/cli.js:13`), repeated pause/unpause logic blocks (`bin/cli.js:378-452`, `bin/cli.js:454-526`)
   - Root cause: iterative growth without extraction or import pruning
   - Recommendation: extract shared interactive selection/action helpers and prune unused imports

4. **List command incurs repeated state reads for interval jobs**
   - Evidence: per-job call to `getNextScheduledRun` (`bin/cli.js:126-128`) which reads state each call (`src/state.js:159-163`)
   - Root cause: convenience API used in loop without batch state snapshot
   - Recommendation: read state once, compute next-run values in-memory

### Positive observations

- State writes are guarded by lock + atomic rename pattern (`src/state.js:24-35`, `src/state.js:112-123`)
- Locking module handles stale pid and process-exit cleanup thoughtfully (`src/lock.js:59-79`, `src/lock.js:14-24`)
- Test coverage breadth improved significantly in runner/state/launchd domains (`src/runner.test.js:454-735`, `src/state.test.js:159-293`, `src/launchd.test.js:303-442`)

## Risk assessment

### Highest risk changes

1. **Scheduler due-logic rewrite (Task 10)**
   - Risk: accidental timing regressions for existing jobs
   - Mitigation: add deterministic tests around representative cron expressions before changing logic

2. **Namespace lifecycle fixes (Task 3)**
   - Risk: deleting wrong plists/registry entries
   - Mitigation: dry-run logging path and explicit namespace/file matching tests

3. **Packaging/dependency cleanup (Task 4)**
   - Risk: breaking existing local workflows relying on file dependency
   - Mitigation: document migration path and validate both local-dev and publish flows

### Medium risk changes

- Command logging changes may alter output format (`Task 5`)
- API behavior change from exit -> throw may impact callers (`Task 9`)

### Low risk changes

- JSDoc/import cleanup and CLI text polish (`Tasks 8 and partial Task 9 docs`)
- Notification hardening with backward-compatible fallback (`Task 6`)
